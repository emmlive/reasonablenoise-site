# RN-3B1C Phase 3 — isolated D1 / private R2 binding adapter

Dependent **draft** on PR #14. No production schema migrated, no Cloudflare bindings added, no upload endpoint changed, no Stripe or payment authorization.

## Engineering model
- The new module validates PNG bytes and a trusted server-side authorization callback, writes a private object key generated by the server, reads the object back, verifies its exact SHA-256 and size, then inserts the metadata into D1.
- D1 PRIMARY KEY and UNIQUE object key prevent record collisions. Consumption uses a **single conditional SQL UPDATE** with `status='issued'`, owner/order, key, checksum, length, and time predicates. Successful consumption requires `meta.changes===1`; the update is the cross-worker replay fence, not an in-memory lock.
- R2 writes and D1 commits are not one atomic distributed transaction. If D1 insertion fails, deletion is attempted; if deletion also fails, an **orphaned private object remains**. It does not authorize checkout. An independently verified sweeper and monitoring are required before activation.
- The R2 readback and initial DB insert are non-atomic relative to later object mutation. Store must be private, use unguessable keys and deny arbitrary overwrite; a read-before-consume digest comparison protects substitutions at consumption, but stronger version/immutability controls and race tests are required.
- This module is **an isolated contract**, not a secure production endpoint. The caller must authenticate a real session and authorize the subject/order relationship. The `authorize` argument must be supplied by trusted server policy, never user controlled.
- Both success paths explicitly report `checkoutEligible:false` and `productionApproved:false`.

## Unmet gates
1. Independently run tests in Windows, build, diff-check, and inspect module/migration. Target 89 tests (74 prior + 15 new).
2. D1 real disposable local SQL migration tests and Worker runtime compatibility; genuine R2-compatible disposable emulator integration tests.
3. Object cleanup/expiry sweeper using reconciled records, monitoring and retention/privacy decisions; failure injection and clock behavior.
4. Read consistency, object overwrite races, D1 schema migration policy, deployment bindings and least privilege security review.
5. Explicit real authentication and customer/order lifecycle, then Stripe idempotency separately; never reuse one-time consumed intents for payment retries without a durable checkout design.
